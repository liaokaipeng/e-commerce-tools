# 开放平台登录链路（开发视角）

> 面向**开发者**：OAuth 授权流程、v2 签名规则、token 刷新与失效语义，以及官方 Open API 的统一调用入口。总体架构见《[架构](架构.md)》；使用者操作见《[新手入门指南](../新手入门指南.md)》“授权店铺”；参数报错排查见《[开发指南](开发指南.md)》§5.1；官方接口资料见《[shopee_api_doc/README.md](shopee_api_doc/README.md)》。

## 1. 授权流程（OAuth）

```
① 录入 App      /openapi/ 页保存 partner_id / partner_key / 环境（prod 生产 / sandbox 沙箱）
       │ POST /api/openapi/app → server/data/openapi-session.json
       ▼
② 授权链接     POST /api/openapi/auth-url → 本地拼接 GET 授权链接（不调接口，约 30 分钟有效）：
       │ partner.shopeemobile.com/api/v2/shop/auth_partner?partner_id=…&timestamp=…&sign=…&redirect=…
       │ 浏览器打开 auth_url，卖家登录选店授权
       ▼
③ 回调换 token  官方跳回 redirect 配置的回调地址（主账号授权只带 code=…&main_account_id=…，**没有 shop_id**）
       │ 内联 HTML 页读 query → POST /api/openapi/auth-callback
       ▼
④ 持久化       官方 /api/v2/auth/token/get 返回 access_token（约 4 小时）/ refresh_token（约 30 天）
       │ 主账号授权以 main_account_id 换取（回调无 shop_id 时），返回的 shop_id_list 全部保存
       │ （授权拿到的初始 token 对可被多个店铺共用，但各店一旦刷新即各自独立，见 §3）
       ▼
⑤ 后续调用     callOpenApi(apiPath, 业务参数, { shopId })：自动签名 + 附带 token，
              过期自动换新（**按 shop_id 逐店刷新、只写回本店**，旧 refresh 立即失效）
```

官方网关：生产 `https://partner.shopeemobile.com`，沙箱 `https://partner.test-stable.shopeemobile.com`；回调 redirect 需与 App 后台配置一致。**后台只做域名校验**：不接受 `127.0.0.1` / `localhost` / `sslip.io` 等指向本机的地址（报 Invalid live redirect url domain）、不能带 `?` 查询参数；没有域名时后台与工具都用默认占位 `https://example.com/`。`validateRedirect` 支持 `auto`（本机域名白名单 + 8765 + `/openapi/callback`，授权后自动换 token）与 `manual`（浏览器跳到任意域名后，把完整链接粘贴回「开放平台」页；也可用转发页或指向 127.0.0.1 的 A 记录实现全自动）。

## 2. 签名规则（v2）

- 业务接口：`base = partner_id + api_path + timestamp + access_token + shop_id`（无 token 时不拼后两项）。
- `sign = HMAC-SHA256(partner_key, base)`（小写 hex）；`auth_partner` 特殊：**不调接口**，授权链接由本地直接拼接为 GET URL（`client.js` 的 `getAuthUrl`）。
- 方法约定：**查询类接口（get_*/search_*）用 GET**——公共参数 + 业务参数全放 query、无 body；**写操作与换 token 用 POST**——公共参数放 query、业务参数放 JSON body；方法用错网关直接 404。
- **access_token/get 刷新接口特殊（生产实测）**：签名 base 只拼 `partner_id + api_path + timestamp`；query 只放 `partner_id/timestamp/sign`；body 为 `{ partner_id: 数字, shop_id: 数字, refresh_token }`——**只用 shop_id、不用 merchant_id**（merchant_id 刷出来的是商户级 token，调店铺级接口会报 `invalid_acceess_token`，见 §3）；id 必须**数字类型**（字符串报格式错）；网关对失效凭证返回误导性文案（"Invalid access_token" / "Your refresh token or shop_id is wrong"），`hintOf` 已翻译为「请重新授权」提示。
- 商户级接口（`get_merchant_info` / `get_shop_list_by_merchant` 等）签名 base 用 `merchant_id` 顶替 `shop_id`，且 query 必须带 `merchant_id`；本工具目前只调店铺级接口，不涉及。
- `timestamp` 为秒级时间（依赖本机时钟）；`error_invalid_timestamp` 等业务错误按 `ERROR_HINTS` 映射中文提示。规则以官方「授权与鉴权」页面为准（developer-guide/20）。

## 3. 路由与复用

- 路由总表见《[架构](架构.md)》§1.1（注册在 `server/openapi.js`）；模块语义上只需记住：**未配置 App 时所有接口一律 400 + 中文提示**。
- **统一调用入口**：新模块只需 `callOpenApi(apiPath, 业务参数, { shopId })`（查询类传 `{ method: 'GET' }`），签名、token 附带、过期自动刷新均由 client 完成；认证错误**强制刷新**一次后重试（`ensureFresh` 的 `force`：token 名义未过期也要真刷新，否则复用的还是那个坏 token，白跑一遍就把店铺标成需重新授权）。
- **刷新入口只有一条（务必复用）**：`ensureFresh(env, shopId, { force })` 取可用 token（未过期复用 / 过期刷新 / `force` 强制刷新），`refreshShopNow(env, shopId)` 是它的强制版；`POST /api/openapi/refresh`（页面单店「刷新」按钮）、`POST /api/openapi/refresh-all/run`（批量按钮）与 `callOpenApi` 的重试都走它。**新增任何刷新路径都必须复用这两个入口，不要再直接调 `refreshToken`**。
- **手动/批量刷新带冷却（`refreshShopNow` = `ensureFresh({ force: true, cooldown: true })`）**：距上次成功刷新不足 `REFRESH_COOLDOWN_MS`（5 分钟）且当前 token 仍有效时直接复用（返回 `mode='cooldown'`、`synced=0`），不发网关请求——连点会把刚轮换的 refresh_token 送去网关，一旦被拒（`isAuthDead`）就会把店铺标成「需重新授权」（刷新后仍报认证错，见 `isAuthFatalAfterRefresh`）。冷却基准是店铺凭证的 `refreshedAt`（刷新成功 / 授权回调时写入）。**`callOpenApi` 的认证失败重试走 `ensureFresh(force)` 且不开冷却**（否则复用的还是那个坏 token，白跑一遍并标失效）。
- **必须按店铺（shop_id）分别刷新，不能用 merchant_id 整组刷（官方口径 + 生产实测）**：官方 `refresh_access_token` 要求「`shop_id` / `merchant_id` … 必须分别刷新」；FAQ138 Q8 说明主账号（CNSC）授权拿到的共享 token 对一旦被某个 id 刷过就不再共享。**实测（2026-09 生产，CNSC 主账号，67 店共用一对 token）**：`merchant_id` 刷新得到的是**商户级 token**——`get_merchant_info` / `get_shop_list_by_merchant` 正常，但拿它调**店铺级接口一律报 `invalid_acceess_token`**（`Invalid access_token, please have a check.`）。曾经的「按 refresh_token 归组、merchant_id 整组续期并把同一新 token 复制给全组店铺」实现表现为：「开放平台」页状态显示有效（本地按到期时间判定）、监控大屏/工具全部报错、**一点刷新就把本来能用的组全刷坏**。因此唯一路径是 `refreshToken`（按 shop_id）+ `saveRefreshResult`（只写回本店）；凭证库里每个店铺各自持有独立 token 对。
- **批量刷新逐店进行（`server/openapi/refresh-all/`）**：开放平台页「批量刷新 token」按钮 → `POST /api/openapi/refresh-all/run`（SSE）。`planRefreshGroups`（纯函数）把每个店铺拆成一个单元（`size=1`、`mode='individual'`），逐个调用 `refreshShopNow`——**不要按 refresh_token 归组去重**（官方要求按 shop_id 分别刷新，见上条）。已失效 / 缺 refresh_token 的店铺直接跳过，事件 `skipped` 带原因，**不额外把店铺标失效**（用户主动点批量刷新不该标死「其实还好」的店铺）。**单飞互斥**：同一时刻只允许一个批量任务（`runningJobId`；校验时确认任务仍在 `jobs` 注册表，被 TTL 回收的陈旧标记自动放行，避免永久锁死），进行中再触发一律回 409。冷却命中的店铺以 `group-done.mode='cooldown'` / `summary.cooled` 计数体现。任务走 `lib/jobs.js`：SSE 断开即取消，前端「取消」调 `POST /api/openapi/refresh-all/cancel`。事件序：`start`（jobId / 总店铺数 / 总单元数 / 跳过的店铺）→ `skipped` / `group-start` / `group-done` → `summary`（或 `cancelled` / `fatal`）。
- **per-shop 锁 + 全局串行链**：同一店铺的并发刷新共享同一个 Promise，跨店铺刷新统一排队，防并发刷新时的踩踏（页面连点「刷新」也只发一次网关请求）。
- **失效凭证自动标记**：`callOpenApi` / 刷新失败确认凭证死透后经 `store.markShopInvalid` 标记 —— 判定口径为 `isAuthFatalAfterRefresh`＝ `isAuthDead` 的误导性文案，**或**「**已强制换新 token 重试仍报 `error_auth` / `error_access_token`**」（这类错误不刷新就标记会误杀，但刷新后仍报就是终态；漏掉它会让店铺状态一直显示「有效」而每次调用都报错）；业务子码 `error_auth_*`（如 `error_auth_product_is_pff`）与权限错误 `error_permission` 都不是凭证问题，不标记。刷新按 shop_id 进行、token 不跨店共享，故**只标记出错的那个店铺**；已标记店铺不再发请求（`ensureFresh` 直接抛错），监控调度器停止采集、大屏显示「待重新授权」；重新授权或调用成功（`clearShopInvalid`）自动清除。**失效店铺不出现在 `/api/openapi/stores`（各工具「选择店铺」数据源）**，但仍保留在 `/api/openapi/status` 供大屏提示。
- 凭证安全：`openapi-session.json` 存 `server/data/`（gitignored）；status 等接口只回打码 token（`maskToken`）；日志只打印 shop_id 与到期时间，不打印 token 全值。

## 4. 重点店铺筛选（important）

店铺涨到几十上百时，用户可在「开放平台」页「③ 已授权店铺」逐店勾选**重点店铺**，给「自动遍历全部店铺」的链路收窄范围。

- **存储**：标记写进 `server/data/openapi-session.json` 的 `shops[env][shopId].important`（非凭证，随凭证文件一起落盘，gitignored、不入库、不进发布包）。
- **判定源唯一**：`store.getImportantIds(env)` 返回该环境全部重点店铺 ID；`store.status()` 的每条店铺带 `important` 字段供页面回显。**改动任何「取店范围」都必须复用它**，否则各处范围会漂移。
- **回落语义**：某环境**有 ≥1 个重点店铺**时「重点集合」生效；**一个都没标记**时回落为全部已授权店铺——保证未启用该功能时行为与从前完全一致。
- **生效范围（目前）**：
  - 监控大屏：`scheduler/registry.refreshShops` 只把重点店铺纳入监控注册表，非重点店铺不进巡检、不进大屏，其未关闭告警自动关闭（见《[监控大屏实现](监控大屏实现.md)》§1）；勾选变化经 `notifyMonitorAuthChanged()` 即时生效并补采。
  - `shopee_skill`：`shops` 默认只列重点店铺，`--shop all` 只对重点店铺执行，`--all-shops` 可忽略筛选（见 `shopee_skill/SKILL.md`）。与其他链路不同的是：**重点店铺全部失效时 CLI 直接报错、不静默回落到全部店铺**（避免 `--shop all` 的写操作打到预期外的店），要扩大范围必须显式加 `--all-shops`。
- **不生效范围**：各工具页（竞价导出 / 取消竞价 / 取消 Hot Listing / 视频上传）的「选择店铺」下拉**不受该筛选影响**，仍展示全部可用店铺——这些页面本就由用户手动选店，`/api/openapi/stores` 不放行筛选。
- **接口**：`POST /api/openapi/shop-important` `{ shopId, important }` → 写标记并通知大屏；`important=false` 取消标记，计数归零时自动回落为全部店铺。
