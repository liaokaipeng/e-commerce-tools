# 灯饰分类体系与差评分析流程

> 本文件描述「每周差评分析」的分类体系、单条评论处理流程与周报聚合口径。

## 一、分类体系总览

### 1.1 层级结构

```
灯饰
  └─ 覆盖品类: 太阳能灯、灯带、灯泡/灯串、泛光灯、感应灯等
      └─ 分类: 14 类（见 1.2）
          └─ 差评点: 每类 2~4 条参考范例，由大模型在范例引导下从原文提炼
```

### 1.2 分类一览（14 类）

| # | 分类 | 关注维度 |
|---|---|---|
| 1 | 安装 | 物理安装、配件 |
| 2 | 配网与上手 | 初次配对、设置体验、遥控 |
| 3 | 功能 | 定时/感应开关、可配置性、响应 |
| 4 | 可靠性 | 损坏、闪烁、发热 |
| 5 | 网络与兼容 | 连接稳定性、供电/协议兼容 |
| 6 | 发光效果 | 亮度、色温、均匀度 |
| 7 | 供电与续航 | 续航、充电、太阳能 |
| 8 | 感应与智能 | 人体感应、光感、联动 |
| 9 | 外观与材质 | 做工、材质、与图片不符 |
| 10 | 噪音与干扰 | 异响、电磁干扰 |
| 11 | 防水与耐候 | 进水、老化、高低温 |
| 12 | 需求 | 功能诉求 |
| 13 | 售后 | 物流、包装、退换 |
| 14 | 其它 | 兜底 |

## 三、单条评论处理流程

### 3.1 流程总览

```
评论(title, text, rating) + product_context
        │
        ▼
┌─────────────────────────────────────┐
│ 第0步: 输入预处理（本地，不调AI）      │
│  无效评论过滤 / 超长截断 / 语言归一    │
└─────────────────────────────────────┘
        │
        ▼
┌─────────────────────────────────────┐
│ 第1步: AI调用 — 分类 + 差评点          │
│  输入: title/text/product_context     │
│       + allowed_categories (14类)     │
│       + category_reference_examples   │
│  输出: {"categories": [...],          │
│         "negative_points": [...]}     │
└─────────────────────────────────────┘
        │
        ▼
┌─────────────────────────────────────┐
│ 第2步: 白名单归一化（本地清洗，不调AI） │
│  categories / negative_points 归一化  │
│  + 调用失败降级与缺口统计              │
└─────────────────────────────────────┘
        │
        ▼
最终输出: category(拼接) / negative_points /
         negative_point(拼接)
```

### 3.2 第 0 步：输入预处理（本地，不调 AI）

| 处理 | 规则 |
|---|---|
| 无效评论过滤 | 无文字、纯表情/符号、系统默认好评直接丢弃，不送 AI |
| 模板化刷评 | 同一文本当周重复 ≥5 次判定为刷评：只记录计数，不逐条分析 |
| 超长截断 | title+text 合计超 500 字截断，保留头部（问题多在前段） |
| 评分入参 | rating 随请求体传入，作为严重度先验信号，不进入提示词 |
| 语言归一 | 非中文评论先翻译为中文再进第 1 步，保证提示词口径统一（翻译用轻量调用，不计入分析调用量） |
| product_context | 固定为「商品标题 + 类目关键属性」（如太阳能灯/感应灯、供电方式、是否智能款），与评论同批带入；缺失时填空字符串，不阻塞流程 |

### 3.3 第 1 步：AI 提取分类 + 差评点

- **参考资料选取**：`LIGHTING_CATEGORY_REFERENCE_EXAMPLES`
  - 字典的 **key 列表 = allowed_categories**（14 类白名单）
  - 字典的 **完整内容 = category_reference_examples**（每个类别的差评点范例）
- **请求体**：`rating`、`title`、`text`、`product_context`、`allowed_categories`（14 类）、`category_reference_examples`（差评点范例）
- **System prompt 要点**：
  > 请对以下灯饰类商品的评论完成两项任务：
  > 1) 判断所属分类，可多选，但不能不选；输出必须且只能从 allowed_categories 中选择，不允许新增类别。
  > 2) 提炼差评点，规则：
  >    - 每条是"问题现象 + 关键量化信息"的简明事实陈述
  >    - 保留数量、比例、时长、价格对比、使用环境等量化信息
  >    - 同一问题的现象/原因/影响合并为一条，不同维度才分开
  >    - 删除无信息量措辞，不照搬情绪化表述
  >    - 每条 ≤30 字，通常 1~3 条，最多 5 条
  >    - 只依据原文提炼，不臆测
  > 信息不足时 categories 和 negative_points 均返回 ["其它"]。
  > 严格返回 JSON：`{"categories": [...], "negative_points": [...]}`。
- **调用参数**：`temperature=0`、`enable_thinking=False`、`response_format={"type": "json_object"}`（保证输出确定性且为合法 JSON）
- **范例的作用**：大模型以 `category_reference_examples` 为风格和粒度基准提炼差评点（如"背胶不牢"级别的短语），同时以 14 类白名单约束归类
- **调用侧约定（不改提示词）**：
  - 单条调用、受控并发（建议 4~8 路），遇网关限流自动退避后重试
  - 超时（如 60s）后重试，最多 2 次；仍失败进入 3.4 的降级处理
  - `temperature=0` 下调用幂等：按评论唯一 ID 缓存结果，重跑/断点续跑时跳过已处理条目
  - 网关凭证不硬编码、日志不打印请求头（仓库红线）

### 3.4 第 2 步：本地归一化兜底

| 处理对象 | 规则 |
|---|---|
| categories | 不在 14 类白名单内 → 替换为「其它」；去重；若同时有确定性类别和「其它」→ 剔除「其它」；为空 → `['其它']` |
| negative_points | 压缩空白、去重、最多保留 6 条；为空 → `['其它']` |
| AI 调用失败（重试后仍超时/限流/JSON 解析失败） | 该条标记为「待分析」（`status=pending`），不计入任何分类与差评点统计；每期输出「待分析缺口数」供人工补跑。**不得静默置为「其它」**——那会把调用故障伪装成分类结果 |

### 3.5 最终输出结构

```python
{
    'categories': ['防水与耐候', '供电与续航'],
    'category': '防水与耐候,供电与续航',
    'negative_points': ['雨天进水后灯珠损坏', '太阳能充电效率低，阴雨天不亮'],
    'negative_point': '雨天进水后灯珠损坏; 太阳能充电效率低，阴雨天不亮',
    'classify_version': 'v1.0',  # 分类体系/提示词版本，改动 §一/§二/提示词时必须 +1
    'status': 'done',            # done / pending（调用失败待分析）
}
```

## 四、周报聚合口径

> 聚合只在周报层进行，不回写单条结果。

### 4.1 差评点归并（跨评论归一化）

- 单条去重只解决「完全相同」，解决不了同一问题的不同表述（"进水了"/"不防水"/"雨天就坏"）；不归并则周报里同一问题有几十种变体，无法聚焦
- 归并方式（二选一或叠加）：
  - 同义词映射表：把变体表述映射到标准问题名（如 `进水/起雾/不防水/雨天就坏 → 进水失效`），映射表随 `classify_version` 一起版本管理
  - 每周对去重后的差评点再做一次聚类调用，产出标准问题名
- 归并后按「出现评论数 × 涉及 SKU 数」排序，每分类输出 Top N（建议 5）

### 4.2 统计口径

| 项 | 口径 |
|---|---|
| 差评率分母 | 当周有效分析评论数（输入过滤后且 `status=done`） |
| 差评率分子 | 命中该分类/差评点的评论数 |
| 拆分维度 | 按 SKU/SPU、按站点、按周（趋势） |
| 缺陷 vs 诉求 | 「需求」类差评点单独成栏，不与故障类混合排序 |

### 4.3 安全问题提级

- 命中安全关键词（发热/起火/冒烟/进水致短路/灯罩破裂等）的差评点，不论排名均在周报标红提级
- 关键词清单随 `classify_version` 一起维护

### 4.4 体系健康度与版本记录

- 每期监控三个数：「其它」分类占比、信息不足（categories 与 negative_points 均为 `["其它"]`）占比、待分析缺口数
- 「其它」或信息不足占比连续 2~3 期上升 → 触发分类体系迭代评审（新增/合并类别，同步改 §一/§二 并 +1 版本号）
- 每期周报头部记录 `classify_version`；跨期对比前先核对版本一致，避免把「改了规则」误读成「问题变多/变少」

## 五、周报执行手册（Runbook）

> 本章是「跑一期周报」的完整操作手册：**每周一的自动化任务与随时手动触发，都按本章执行**（同一事实只写一处，任务消息只放指针，不复述细则）。
> 手动触发方式：对 agent 说「按 `每周差评分析/灯饰分类体系与分类流程.md` 第五章跑一期周报」即可，不依赖任何定时任务。
> 全程只读：不调用任何写接口，不改 `server/` 目录与任何凭证文件，不提交 git。

### 5.1 链路总览

```
重点店铺评论（get_comment 拉取 + 本地过滤）
  → 翻译 + 分类 + 差评点提炼（按 §三，由执行会话 inline 完成）
  → Excel（exceljs，落盘 reports/）
  → 邮件（send-mail.js，附件发送）
```

### 5.2 取数（shopee-query）

- 命令：`node shopee_skill/cli.js call get_comment --shop all --all`（`--shop all` 即重点店铺口径，一个都没勾选时回落为全部已授权店铺）
- 口径：接口**无星级/时间过滤参数**，`rating_star` 与 `create_time` 必须拉取后本地过滤（1~3 星且评论时间落在过去 7 个自然日，按站点当地日，时区偏移参考 `.trae/local/daily-yoy-report.js` 顶部 `REGION_OFFSET`）；评论按时间倒序，翻到早于时间窗即可停页；首页 `cursor` 用 `--param cursor=0`（传空串会被本地必填校验判为缺失）
- **必须按 `comment_id` 去重**：游标翻页偶发把同一条评论返回两次（实测重复出现在页面边界），入口就去重，否则明细有重复行、差评率分母虚高
- 商品标题：`v2.product.get_item_base_info` **按店**补齐（`item_id_list` 逗号分隔、每批 50）；某店取不到标题时留 `item<id>`，不阻塞
- 单店凭证失效：跳过该店并在报告「异常提醒」列出；全部失效：仍要发邮件说明，不要静默空跑

### 5.3 翻译与分类

按 §三 执行：输入预处理（§3.2）→ 提示词与提炼规则**逐字沿用**（§3.3）→ 白名单归一化兜底（§3.4）→ 输出结构（§3.5）。翻译与分类由执行会话 inline 完成（相当于 temperature=0 的确定性执行），**不需要外部 LLM 配置**。重点店铺均为灯饰店，有文字评论全部进入 14 类分类；无文字评论只计入统计、不归因。

### 5.4 Excel 规范（exceljs，落盘 `reports/差评分析_<起>_<止>.xlsx`）

- Sheet「明细」**只含有文字差评**（纯星级差评不进 Excel，但仍计入统计），固定 12 列：店铺、站点、商品标题、item_id、订单号、星级、评论时间(PH)、原文、中文译文、分类、差评点、带图/视频；首行冻结 + 自动筛选。**不要加**标题译文、评论标题、状态等额外列
- Sheet「统计」按 §四口径，依次七节：
  1. 总体（分店铺 + 合计：窗口内评价 / 1★ / 2★ / 3★ / 差评合计 / 差评率）
  2. 分类占比（分母 = 有文字差评数）
  3. Top 差评点（归并后，按出现条数排序）
  4. 缺陷 vs 诉求（「需求」类单列）
  5. 安全提级（关键词：发热/起火/冒烟/进水致短路/灯罩破裂，不论排名）
  6. 差评集中商品 TOP
  7. 健康度三指标（「其它」占比、信息不足占比、待分析缺口）
- 统计 sheet 顶部注明：纯星级差评条数不列入明细、但已计入统计

### 5.5 发邮件（send-mail 技能）

```bash
node .trae/local/send-mail.js --to <两个默认收件人> \
  --subject "重点店铺周差评分析 <起>~<止>" \
  --body-file <摘要文件> --attach <xlsx路径>
```

- 收件人：send-mail 技能规定的两个默认收件人（地址以 `.trae/local/` 下维护的为准，可参考 `.trae/local/daily-yoy-report.js` 顶部 `RECIPIENTS`）；真实地址不要写进仓库任何文件
- `--attach` 已内置（multipart/mixed、中文文件名 RFC 5987 编码），直接用，**不要改动 send-mail.js**
- 正文放统计摘要：评价总量、1~3 星量与差评率、有文字/无文字条数、分类占比、Top 差评点、安全提级、异常提醒
- 发信失败（授权码未填/认证失败/网络异常）：Excel 与摘要落盘 `reports/` 并说明原因，不要反复重试

### 5.6 汇报

只报四件事：① 邮件是否发送成功；② Excel 路径；③ 核心结论（评价总量、1~3 星量与差评率、Top3 分类、Top3 差评点、安全提级条目）；④ 异常提醒（失效店铺、待分析缺口等）。

### 5.7 已知坑

- `get_comment` 无星级/时间过滤、首页 cursor 传 `0`、翻页偶发重复——完整口径见 `shopee_skill/SKILL.md` 排错节
- 评价接口**没有独立的「评论标题」字段**；正文里的 `Appearance:` / `Quality:` 等是买家分维度打分的标签，不是标题
- 附件邮件的正文段必须带 `Content-Transfer-Encoding: base64`（send-mail.js 已处理，改它时别回退）
